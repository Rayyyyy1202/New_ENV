# 微信 / 飞书等渠道接入方案(生产版)

> 当前演示里的"渠道接入 + 工单收件箱 + 自动受理"是用内置假数据模拟的。
> 本文说明真要打通微信 / 飞书 / 企业微信 / 钉钉 / 邮箱时,生产版怎么落地。
> 目标:**工单从聊天工具自动流入 → AI 读懂消息与附件、提取指令 → 跑完对标自动填表 →
> 高置信直接回写,异常推回群里找人确认。**

---

## 一、总体架构

```
微信/企业微信/飞书/钉钉/邮箱
        │  (1) 事件回调 / 消息订阅 / 收件
        ▼
   渠道适配层 (Channel Adapters)        ← 验签、解密、统一成内部事件
        │  (2) 归一化为「工单事件」
        ▼
     工单服务 (Work-Order Service)       ← 去重、落库、状态机(待受理/处理中/待确认/完成)
        │  (3) 入队
        ▼
   消息队列 (Kafka / RabbitMQ / Redis)
        │  (4) 消费
        ▼
   Agent 编排器 (Orchestrator)
        ├─ 意图/指令提取 (LLM)
        ├─ 附件解析 (装箱单 xlsx/pdf/csv/图片 OCR)
        ├─ 对标流水线 (翻译→语义查库→亚马逊搜索→三重核验→择优)
        └─ 决策:高置信自动通过 / 异常 → 人工
        │  (5) 回写 + 回复
        ▼
   结果回写(数据库) + 渠道回复(把结果/待确认卡片发回原群)
```

前端(本演示这套 UI)作为**人工审核台**:订阅工单服务的状态,展示待确认工单、AI 已填好的对标、一键通过/驳回。

## 二、各渠道怎么接

| 渠道 | 接入方式 | 关键点 |
|---|---|---|
| **飞书 / Lark** | 自建应用 + **事件订阅**(`im.message.receive_v1`) | 用 `tenant_access_token`;附件经 `im/v1/files`、`im/v1/images` 下载;回复用 **消息卡片**(可带"通过/驳回"按钮,回调到卡片 action) |
| **企业微信** | 自建应用 + **接收消息回调** | URL 验签(`msg_signature`)+ AES 解密;附件用 `media/get`;可发**模板卡片消息**带按钮 |
| **微信(个人)** | 无官方开放接收个人消息的能力 | 生产上走**企业微信**或**微信客服**;不要用非官方 hook,违规且不稳定 |
| **钉钉** | 机器人 + **事件订阅 / Stream 模式** | Stream 模式免公网回调;附件走钉盘/媒体接口;可发可交互卡片 |
| **邮箱** | IMAP 拉取 / 邮件服务商 Webhook(SES、Mailgun) | 解析 MIME 取正文与附件;回复用 SMTP |

**统一抽象**:每个渠道实现同一个 `ChannelAdapter` 接口:
```ts
interface ChannelAdapter {
  verify(req): boolean                 // 验签
  parse(req): IncomingMessage          // 解密 + 归一
  downloadAttachment(ref): Promise<Buffer>
  reply(threadId, payload): Promise<void>   // 文本 / 交互卡片
}
```
新增渠道只需实现这个接口,上层流水线不变。

## 三、从聊天记录到"指令"

1. **取上下文**:不止取最后一条,拉取该会话最近 N 条 + 附件,拼成上下文。
2. **LLM 提取**:用结构化输出让模型产出工单:
   ```json
   {
     "intent": "find_amazon_comparables",
     "marketplace": "amazon.de",
     "exclude_brands": true,
     "scope": "all | single",
     "target_item": "莲蓬头 | null",
     "attachments": ["装箱单_2406.xlsx"]
   }
   ```
   (演示里 `engine/review.ts` 的 `parseCommand` 就是这步的本地简化版。)
3. **附件解析**:xlsx/csv 用表格解析;pdf 用版面解析;图片清单走 **OCR**;统一成内部装箱单结构。
4. **澄清回路**:字段缺失或意图不明时,机器人**在原群回一条澄清问题**,而不是瞎跑。

## 四、自动受理 / 人在环(对应演示里的"自动受理"开关)

按**置信度**与**风险**分流:

- **高置信 + 低风险** → 自动通过、自动回写、把结果卡片回到群里(留"撤销"入口)。
- **低置信 / 命中风险**(疑似品牌、材质不符、原产地非中国、相关性低)→ 标 **待人工复核**,
  把"AI 已填好 + 待确认"的卡片推送给审核人(本 UI 或群内交互卡片)。
- **失败 / 缺数据** → 回群澄清或转人工。

阈值、风险规则、自动通过白名单都做成可配置(对应演示的 `roi.ts` / `review.ts` 里的 needsReview 逻辑)。

## 五、可靠性 / 合规 / 安全

- **幂等**:同一条消息可能重复回调,按渠道消息 ID 去重。
- **异步**:回调要秒级 ACK,真正处理丢队列后台跑(对标可能几十秒)。
- **限流 / 重试**:亚马逊抓取、LLM 调用都要退避重试与配额控制。
- **密钥管理**:各渠道 token / `OPENAI_API_KEY` 等存密钥管理服务(KMS / Vault / 平台环境变量),
  绝不进前端、不进代码库(本演示已用 Vercel 服务端环境变量示范)。
- **审计**:每个工单留全链路日志(原始消息、提取指令、候选、核验、谁审批),便于报关合规追溯。
- **数据隔离**:多租户按客户隔离数据与配额。

## 六、与本演示代码的对应关系

| 演示(模拟) | 生产(真实) |

## 七、落地步骤建议

1. 先接**一个**渠道(推荐飞书或企业微信,卡片交互完善)跑通闭环。
2. 工单服务 + 队列 + 审核台(复用本 UI)。
3. 对标流水线逐段接真:翻译(已就绪)→ 真实亚马逊抓取 → EUIPO 商标查询 → 材质/原产地抽取。
4. 上自动受理分流 + 群内交互卡片确认。
5. 灰度 + 审计 + 配额,再扩更多渠道。
